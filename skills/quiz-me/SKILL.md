# /quiz-me — 프로젝트 이해도 점검 퀴즈

코드베이스를 **실제로 읽고** 문제를 출제합니다. 일반론 문제를 내지 않습니다.
모든 문항은 실존하는 파일·함수·설정을 근거로 하며, 채점 시 근거 파일 경로를 함께 제시합니다.

## 인자

| 인자 | 기본값 | 설명 |
|------|--------|------|
| `[영역 또는 경로]` | 전체 | 특정 영역 한정 (예: `백엔드`, `인증`, `src/api/`) |
| `--count N` | 5 | 문항 수 (1~15) |
| `--level` | normal | `easy`=구조/위치, `normal`=흐름/책임, `hard`=엣지케이스/설계의도 |
| `--open` | off | 객관식 대신 서술형으로 출제 |

예: `/opensmith:quiz-me 인증 --count 7 --level hard`

---

## Phase 1: 코드베이스 스캔

출제 전에 **반드시** 코드를 읽습니다. 이 단계를 건너뛰고 문제를 만들지 않습니다.

1. 진입점/설정 파악
   - `README.md`, `CLAUDE.md`, `.opensmith/config.json`, `package.json` / `*.csproj` / `requirements.txt` / `go.mod`
2. 디렉토리 구조 파악 — Glob으로 상위 2~3 depth 트리 확보
3. 핵심 모듈 식별 — 라우팅/엔트리포인트, 데이터 모델, 외부 연동 지점
4. 최근 변경 파악 — `git log --oneline -20`, 최근 커밋이 건드린 파일
5. 프로젝트 고유 규칙 확인 — `.claude/skills/never-do.md`, `frontend-patterns.md`, `backend-patterns.md` (있으면)

`[영역]` 인자가 있으면 해당 영역으로 스캔을 좁힙니다.

### 스캔 결과 정리 (내부용, 사용자에게 출력하지 않음)

```
- 사실 목록: [파일 경로] → [그 파일이 실제로 하는 일]
- 흐름 목록: [요청/이벤트] → [거쳐가는 파일 순서]
- 규칙 목록: [프로젝트 고유 결정] → [근거 파일:라인]
```

## Phase 2: 출제

### 문항 카테고리 (골고루 섞어서 출제)

| 카테고리 | 묻는 것 | 예시 |
|----------|---------|------|
| 구조 | 어디에 무엇이 있는가 | "회원가입 요청을 처리하는 파일은?" |
| 흐름 | 데이터가 어떻게 흐르는가 | "로그인 시 토큰이 발급되어 저장되기까지 거치는 순서는?" |
| 책임 | 왜 이 모듈이 이걸 하는가 | "X 검증이 컨트롤러가 아니라 서비스에 있는 이유는?" |
| 규칙 | 이 프로젝트만의 결정 | "이 프로젝트에서 직접 fetch를 쓰면 안 되는 이유는?" |
| 엣지 | 실패하면 어떻게 되는가 | "DB 연결이 끊기면 이 핸들러는 어떻게 동작하나?" |

`--level hard`는 책임/엣지 비중을 높이고, `easy`는 구조 비중을 높입니다.

### 출제 원칙 (NEVER DO)

1. **코드에서 확인하지 못한 내용을 출제하지 않는다.** 추측으로 정답을 만들지 않는다.
2. **일반 지식 문제를 내지 않는다.** ("REST란?" ❌ / "이 프로젝트의 REST 엔드포인트는 어디에 정의되나?" ⭕)
3. **정답이 하나로 확정되지 않는 문제를 내지 않는다.** 서술형이라도 채점 기준이 명확해야 한다.
4. **답을 문제 안에 흘리지 않는다.** 오답 보기도 그럴듯해야 한다 (실존하는 다른 파일/모듈 사용).
5. **한 번에 모든 문제를 던지지 않는다.** 1문항씩 출제하고 답을 받은 뒤 다음으로 넘어간다.

### 출제 형식

객관식(기본)은 `AskUserQuestion`으로 4지선다를 제시합니다.
`--open`이면 텍스트로 서술형 질문을 던지고 자유 답변을 받습니다.

```
문제 3/5 · 흐름 · normal

사용자가 채팅 메시지를 보낼 때, 요청이 DB에 저장되기까지 거치는 순서로 맞는 것은?
```

**모른다는 답도 허용합니다.** "모르겠음"을 고르면 감점 없이 해설로 넘어갑니다(점수는 오답 처리하되, 이해도 리포트에서 "미학습" 으로 별도 집계).

## Phase 3: 채점 및 해설

각 문항 답변 직후 즉시 채점합니다. 다음 문제까지 미루지 않습니다.

```
✅ 정답 (또는 ❌ 오답 — 정답: B)

근거: src/api/chat/route.ts:42 → services/chatService.ts:88 → repositories/messageRepo.ts:15
해설: 라우터는 검증만 하고 저장 책임은 repository에 있습니다. service는 그 사이에서
      권한 체크와 트랜잭션 경계를 담당합니다.
```

- 근거 경로는 **반드시 실존하는 파일:라인**으로 제시 (Read로 확인한 것만)
- 서술형은 핵심 키워드 포함 여부로 부분 점수 (0 / 0.5 / 1)
- 오답이면 사용자의 답이 왜 틀렸는지도 한 줄로 짚어줍니다

## Phase 4: 이해도 리포트

전 문항 종료 후 출력합니다.

```markdown
# 이해도 리포트

점수: 3.5 / 5 (70%)

| # | 카테고리 | 결과 | 주제 |
|---|----------|------|------|
| 1 | 구조 | ✅ | 라우팅 위치 |
| 2 | 흐름 | ❌ | 메시지 저장 경로 |
| 3 | 규칙 | ✅ | never-do 규칙 |
| 4 | 책임 | ◐ | 서비스 레이어 역할 |
| 5 | 엣지 | ❌ | DB 장애 시 동작 |

## 강한 영역
- 디렉토리 구조와 프로젝트 고유 규칙은 잘 파악하고 있습니다.

## 약한 영역
- **레이어 간 책임 분리** — service와 repository의 경계를 혼동하고 있습니다.
  → 읽어볼 것: services/chatService.ts, repositories/messageRepo.ts
- **에러 처리 경로** — 예외가 어디서 잡히는지 파악되지 않았습니다.
  → 읽어볼 것: middleware/errorHandler.ts

## 다음 단계
- `/opensmith:quiz-me 에러처리 --level hard` 로 약한 영역만 재점검
```

### 리포트 저장 (선택)

3문항 이상 오답이면 저장을 제안합니다:

```
약한 영역이 여러 개 있습니다. 리포트를 .opensmith/quiz-report.md 에 저장할까요?
```

동의 시에만 작성합니다. 묻지 않고 파일을 만들지 않습니다.

## Memory Bank 연동

`.opensmith/memory-bank/` 가 존재하면:

- 반복적으로 틀리는 영역을 fact로 기록
  - type: `pattern`
  - fact: `"사용자가 [영역]의 [개념]을 반복 오답 — 설명 시 이 부분을 먼저 짚을 것"`
- 다음 `/opensmith:quiz-me` 실행 시 이전 약한 영역을 우선 출제

Memory Bank가 없으면 이 단계는 조용히 스킵합니다.

---

## 중단 조건

1. 사용자가 "그만", "됐어" → 여기까지의 결과로 리포트 출력 후 종료
2. 코드베이스가 비어있거나 읽을 소스가 없음 → "출제할 코드가 없습니다" 안내 후 종료
3. `[영역]` 인자에 해당하는 코드를 못 찾음 → 찾은 영역 목록을 보여주고 다시 선택 요청
